# Phase 2 설계 메모

## 왜 Firebase 저장보다 수행평가 입력기를 먼저 만드는가

이 프로젝트에서 가장 불확실하고 중요한 부분은 수행평가 세부기준의 데이터 모델이다.
저장 기능부터 만들면 잘못된 데이터 구조가 Firestore 문서 구조와 UI 전체에 퍼질 수 있다.

따라서 Phase 2에서는 메모리 상태만 사용하여 구조를 빠르게 검증한다.

## 영역별 평가와 전체 단일기준

현장 사례는 크게 두 축을 모두 지원해야 한다.

### 영역별

100점
- 내용 30
- 표현 30
- 전달력 40

각 영역은 서로 다른 ScoringModel을 사용할 수 있다.

### 전체 단일기준

예: 자유투
- 10개 성공 100
- 9개 성공 90

영역을 억지로 만들지 않는다.

Domain validation은 두 방식을 동시에 사용하는 것을 오류로 본다.

## 왜 UI에 반영비율/점수 검증 코드를 넣지 않았는가

React UI는 값을 변경하고 보여주는 역할만 한다.
검증은 `domain/validation.ts`와 `domain/scoring-model-validation.ts`가 담당한다.

이렇게 해야 향후 다음에서도 같은 규칙을 재사용할 수 있다.

- 교사용 화면
- 관리자 검토
- 서버 저장 전 검증
- PDF 생성 전 검증
- NEIS Export 전 검증

## 왜 초기 예시 데이터를 별도 파일로 분리했는가

프로토타입 예시값은 제품의 공식 업무 규칙이 아니다.
따라서 UI 컴포넌트나 Domain에 하드코딩하지 않고 `ui/prototype/` 아래 fixture로 격리하였다.

실제 저장 기능이 들어오면 이 fixture는 개발용 예시로만 남거나 제거할 수 있다.

## Custom Table을 아직 구현하지 않은 이유

사용자 정의 표는 자유도가 높지만 구조화 검증과 향후 NEIS 연계에 불리하다.
먼저 구조화된 네 유형으로 실제 사례를 최대한 수용한 뒤, 정말 필요한 예외의 성격을 보고 구현한다.

## 현재 구조의 단점

1. 모델 종류를 추가할 때 domain union, validation, factory, UI 연결 지점을 각각 수정해야 한다.
   - 의도적인 명시성이다.
   - 현재 규모에서 동적 플러그인 시스템은 오히려 유지보수를 어렵게 한다.

2. 숫자 입력칸을 완전히 비우면 프로토타입에서는 0으로 처리된다.
   - 실제 교사용 폼 단계에서는 Form Draft와 Domain Model을 분리하여 빈 입력 상태를 더 자연스럽게 처리할 수 있다.

3. 평가방식 전환 시 기존 세부기준이 초기화된다.
   - Phase 2는 구조 검증용이라 단순화하였다.
   - 실제 제품에서는 변경 전 확인 또는 임시 보관 UX를 검토한다.

4. 현재 상태는 브라우저 메모리에만 있다.
   - 새로고침 시 초기 예시로 돌아간다.
   - 의도된 Phase 2 범위이다.
