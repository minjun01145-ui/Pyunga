# 수행평가 세부계획 설계

## 문제 정의

수행평가 세부계획은 학교별 차이뿐 아니라 같은 학교의 교사·교과·평가과제마다 채점표 구조가 달라질 수 있다.

따라서 하나의 고정 표를 강제하지 않는다. 동시에 모든 사용자가 자유표만 사용하게 두어서도 안 된다.

목표는 **공통 데이터는 구조화하고, 실제로 구조화하기 어려운 예외만 제한된 custom table로 처리**하는 것이다.

## 기본 구조

권장 논리 구조:

```text
PerformanceAssessment
  ├─ 기본정보
  │   ├─ 평가명
  │   ├─ 반영비율
  │   ├─ 만점
  │   ├─ 실시시기/횟수
  │   ├─ 평가방법
  │   └─ 성취기준
  ├─ Group[] (선택, 1단계만)
  │   └─ EvaluationSection[]
  │       └─ ScoringModel
  └─ 또는 wholeAssessmentScoringModel
```

그룹은 `과정/결과`, `내용/표현`처럼 상위 묶음이 실제 문서에 필요한 경우에만 사용한다.

재귀적인 무한 트리는 만들지 않는다. 지원 계층은 최대 다음 정도로 제한한다.

```text
수행평가 → 그룹(선택) → 평가요소/채점영역 → 채점기준
```

현재 코드의 `EvaluationSection` 및 `wholeAssessmentScoringModel` 구조는 유지한다. Group 도입은 실제 UI/출력 사례를 검증한 뒤 명시적인 Domain 변경으로 수행한다.

## ScoringModel

표준 구조화 유형은 다음을 기본으로 한다.

### level_table

수준별 배점.

예:

- 상 10점
- 중 8점
- 하 6점

### threshold_table

횟수/기록/수량/구간에 따른 배점.

예:

- 10회 성공: 10점
- 8~9회: 8점
- 6~7회: 6점

### criterion_count

여러 조건 중 충족 개수에 따른 배점.

예:

- 5개 충족: 10점
- 4개 충족: 8점
- 3개 충족: 6점

### additive_rubric

여러 평가요소의 점수를 합산.

예:

- 내용 10점
- 표현 5점
- 발표 5점

### custom_table

기존 구조화 유형으로 자연스럽게 표현되지 않는 실제 예외를 위한 fallback.

`custom_table`을 기본 선택지로 앞세우지 않는다. 구조화 검증이 어려워지고 향후 출력/통계/NEIS 연계가 약해지기 때문이다.

## 교사용 UX

교사에게 내부 기술명(`level_table`, `criterion_count`)을 노출하지 않는다.

예시 선택 UI:

- 수준별 채점 (상/중/하 등)
- 구간·기록별 채점
- 조건 충족 개수별 채점
- 평가요소별 합산
- 직접 표 만들기 (예외)

각 방식은 작은 실제 예시 표와 함께 보여주는 것을 권장한다.

교사는 수행평가 기본정보를 입력한 뒤 평가요소/채점영역을 추가하고, 각 영역별로 채점방식을 선택한다.

## 공통 정책과 평가별 Override

다음과 같은 규정은 학교 공통 정책으로 설정되는 경우가 많다.

- 결시자/미응시자 처리
- 전입생 처리
- 기본점수 정책
- 표절/미제출 처리

동일 규정을 수행평가마다 복사 입력하게 하지 않는다.

```text
School Evaluation Policy
       ↓ 기본 적용
PerformanceAssessment
       └─ 필요할 때만 override
```

단, 학교별 실제 양식에서 수행평가별 별도 기재가 필수인 경우 출력 Template이 공통 정책을 해당 위치에 표시할 수 있어야 한다.

## 자동 검증

검증은 React 컴포넌트가 아니라 Domain/Application에서 수행한다.

필수 검증 예:

- 수행평가 반영비율 및 전체 평가 반영비율 합계
- 수행평가 만점과 평가영역 최고점 합계의 일치
- additive rubric 세부항목 최고점 합계
- criterion_count의 충족 개수 중복/누락
- threshold 범위의 중복 또는 역전
- 점수 범위 및 최고점 일관성
- 학교/교육청 규정에 따른 최소 수행평가 비율 등

규정성 검증은 학년도/지역/교과에 따라 달라질 수 있으므로 코드 곳곳에 숫자를 하드코딩하지 않고 Rule/Policy 계층에서 관리한다.

## Form Draft와 Domain Model

교사가 숫자 입력칸을 비워둔 상태와 실제 값 `0`은 다르다.

제품 UI 단계에서는 Form Draft와 Domain Model을 분리하여 입력 중 상태를 자연스럽게 처리한다. 저장/제출/검증 시점에 Domain으로 변환한다.

## 구현 단계

1. 현재 4개 구조화 ScoringModel 프로토타입 검증
2. 실제 학교 문서 사례를 각 모델로 재현
3. 수행평가 기본정보(시기/방법/성취기준 등) 연결
4. 교사용 시각적 방식 선택 UI
5. 필요성이 확인되면 Group 1단계 도입
6. 정말 남는 예외를 확인한 뒤 custom_table 편집기 구현
7. Render POC로 병합 셀/긴 채점기준 출력 검증

새 ScoringModel type은 "미래에 필요할 것 같아서" 추가하지 않는다. 기존 모델로 표현되지 않는 실제 사례가 확인된 경우에만 추가한다.
